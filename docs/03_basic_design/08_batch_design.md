# バッチ設計

## 1. 目的

本書は、本システムの初期リリースに必要な定期処理・非同期処理の方針を定義する。

対象は、保守期限通知、プラン上限警告、Freeトライアル期限確認、CSV処理、バックアップ、データ整理である。

## 2. バッチ一覧

| ID | バッチ名 | 概要 | 初期対象 |
|---|---|---|:---:|
| B-001 | 保守期限通知バッチ | 保守契約の終了日が近い場合にメール通知する | ○ |
| B-002 | プラン上限警告バッチ | 利用量が上限に近づいた場合に管理者へ通知する | ○ |
| B-003 | Freeトライアル期限確認バッチ | Freeプランの期限到来・期限超過を検知する | ○ |
| B-004 | CSVインポート処理 | CSV取込を検証・登録し、履歴を保存する | △ |
| B-005 | CSV一時ファイル整理バッチ | 一時ファイルを削除する | ○ |
| B-006 | DBバックアップバッチ | DBバックアップを取得する | ○ |
| B-007 | 通知ログ整理バッチ | 古い通知ログの整理・保持期間管理を行う | △ |
| B-008 | 操作履歴整理バッチ | 将来拡張の監査ログ保持期間を管理する | 将来 |
| B-009 | クラウド同期バッチ | AWS等のクラウド資産を同期する | 将来 |

凡例: ○=初期必須、△=初期追加対象または簡易対応、将来=初期対象外

## 3. バッチ詳細

## 3.1 B-001 保守期限通知バッチ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日 |
| 実行時刻 | 09:00 |
| 対象 | `notification_enabled = true` の保守契約 |
| 条件 | `end_date - notification_days_before <= 現在日付` かつ `end_date >= 現在日付` |
| 通知先 | 保守契約連絡先、DC連絡先、テナント管理者 |
| 重複抑止 | 同一契約・同一宛先への送信済みログを確認 |
| 失敗時 | 対象通知のみFAILEDとして後続処理を継続 |

## 3.2 B-002 プラン上限警告バッチ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日 |
| 実行時刻 | 09:30 |
| 対象 | 有効テナント |
| 条件 | DC、ラック、機器、IPサブネット、ユーザーの使用率80%以上 |
| 通知先 | テナント管理者 |
| 重複抑止 | 同一対象は原則1日1回まで |

## 3.3 B-003 Freeトライアル期限確認バッチ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日 |
| 実行時刻 | 10:00 |
| 対象 | Freeプランのテナント |
| 条件 | 利用開始日から14日経過、または期限前通知対象 |
| 動作 | 期限前通知、期限超過時は `TRIAL_EXPIRED` 扱いとして閲覧・CSVエクスポート・プラン変更のみ許可 |
| 許可操作 | ログイン、参照、CSVエクスポート、契約プラン確認、有料プランへの変更 |
| 禁止操作 | 登録、更新、削除、CSVインポート、ユーザー招待、オプション追加のみの購入 |

## 3.4 B-004 CSVインポート処理

CSVインポートは初期追加対象とする。初期リリースで実装する場合は以下を基本とする。

| 項目 | 内容 |
|---|---|
| 実行方式 | 小規模ファイルは同期処理、大きいファイルは非同期処理を検討 |
| 履歴 | `csv_import_history` に結果を保存 |
| エラー | `csv_import_error` に行単位エラーを保存 |
| 権限 | テナント管理者、運用者のみ実行可能 |
| 上限 | プラン上限を超える場合は登録不可 |

## 3.5 B-005 CSV一時ファイル整理バッチ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日 |
| 対象 | CSV出力・取込の一時ファイル |
| 保持目安 | 1〜7日 |
| 注意 | 履歴情報はDBに保持し、ファイル削除後も結果確認可能にする |

## 3.6 B-006 DBバックアップバッチ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日 |
| 実行時刻 | 深夜帯 |
| 対象 | MariaDB |
| 保持期間 | 初期は7〜30日を目安 |
| 失敗時 | 管理者へ通知、ログ記録 |

## 4. 実行方式

- Spring Schedulerを基本とする。
- 本番で複数台構成にする場合は、同一バッチの多重実行を防止する仕組みを導入する。
- バッチ開始・終了・失敗はログに記録する。
- バッチ処理はテナント単位で分割し、特定テナントの失敗で全体が停止しないようにする。

## 5. エラー時対応

| 種別 | 対応 |
|---|---|
| 対象データ不整合 | 対象レコードをスキップし、エラー記録 |
| メール送信失敗 | 通知ログをFAILEDに更新 |
| DB接続失敗 | バッチ全体を失敗として管理者通知 |
| CSV行エラー | 行単位でエラー記録し、可能なら他行は継続 |
| バックアップ失敗 | 管理者通知、再実行対象 |

## 6. 後続確認事項

| 項目 | 確認内容 |
|---|---|
| CSVインポートの初期対象 | 機器、ラック、IPサブネット、保守契約のどこまで含めるか |
| バックアップ保持期間 | プラン別差分を設けるか |
| バッチ実行基盤 | Spring Schedulerのみで開始するか、外部ジョブ管理を使うか |
