# DB設計方針

## 1. 目的

本書は、本システムの基本設計におけるDB設計方針を定義する。

詳細なテーブル定義は詳細設計で定義し、本書ではDB方式、共通カラム、制約、インデックス、マイグレーション、バックアップの方針を整理する。

## 2. DB方式

| 項目 | 方針 |
|---|---|
| DBMS | MariaDB |
| 文字コード | utf8mb4 |
| 照合順序 | 日本語・英数字検索に支障がない照合順序を採用 |
| テナント分離 | 単一DB・単一スキーマ・tenant_idによる論理分離 |
| マイグレーション | Flyway等のDBマイグレーションツールを利用 |

## 3. 共通カラム方針

主要な業務テーブルには以下を付与する。

| カラム | 内容 |
|---|---|
| tenant_id | テナント分離用ID。業務データでは原則必須 |
| created_by | 作成者ユーザーID |
| created_at | 作成日時 |
| updated_by | 更新者ユーザーID |
| updated_at | 更新日時 |
| deleted | 論理削除フラグ |

## 4. 主なテーブル領域

| 領域 | 主なテーブル |
|---|---|
| テナント・契約 | tenant, subscription_plan, tenant_add_on |
| ユーザー・権限 | app_user, role, user_role |
| ロケーション | region, data_center, building, floor, area, rack_row, rack |
| 機器 | device |
| IP管理 | ip_subnet, ip_address |
| 保守契約 | maintenance_contract, maintenance_contract_device |
| 連絡先・タグ | contact, data_center_contact, tag, tagged_resource |
| 通知 | notification_setting, notification_log |
| 操作履歴 | audit_log |
| CSV | csv_export_history, csv_import_history, csv_import_error |
| 将来拡張 | cloud_account, cloud_resource |

## 5. 制約方針

| 種別 | 方針 |
|---|---|
| NOT NULL | 必須項目に設定する |
| UNIQUE | テナント内一意の名称・コードに設定する |
| FOREIGN KEY | 参照整合性が必要な主要関連に設定する。ただし論理削除との相性に注意する |
| CHECK | DBMS互換性を考慮し、必要に応じてアプリケーション側で制御する |

## 6. インデックス方針

- 業務検索では `tenant_id` と `deleted` を含むインデックスを基本とする。
- 一覧でよく利用する検索条件、ソート条件には複合インデックスを検討する。
- 正式名称、ホスト名、CIDR、契約終了日など、検索頻度の高い項目を対象にする。
- 過剰なインデックスは登録・更新性能を下げるため、初期は主要検索に絞る。

## 7. 論理削除方針

- 主要業務データは原則として論理削除とする。
- Repository検索では `deleted = false` を必須条件とする。
- 親データ削除時に子データが存在する場合は、Service層で削除可否を判定する。
- 履歴性が高い通知ログ、CSV履歴は原則として物理削除しない。操作履歴はプラン別保持期間に従い、期限超過後に削除またはアーカイブする。

## 7.1 論理削除後の一意性チェック

通常検索は `deleted = false` を基本とするが、業務上の識別子は削除済みデータを含めて重複禁止とする。

| 方針 | 対象例 | 実装方針 |
|---|---|---|
| 削除済みを含めて重複禁止 | ユーザーメール、機器シリアル番号、保守契約番号、IPサブネットCIDR、有効IPアドレス | DBユニーク制約を優先し、論理削除条件付き制約が難しい場合はApplication Serviceで削除済みを含めて照合する |
| 有効データ内で重複禁止 | データセンター正式名称、ラック名、タグ名、地域名、別名 | `deleted = false` の範囲で重複禁止。削除後の名称再利用は許容する |
| 履歴・ログ | 通知ログ、CSV履歴 | 原則削除せず、名称再利用判定の対象外 |

名称・表示名は運用上の変更や再作成があり得るため、識別子ではなく表示用項目として扱う。削除済みを含めて重複禁止する項目は、詳細設計でテーブル単位にユニーク制約またはService側検証を定義する。


## 7.2 操作履歴保持方針

- 初期リリースでは `audit_log` に操作履歴を保存する。
- 保存対象は、ログイン成功/失敗、テナント管理、登録、更新、削除、ユーザー招待、再招待、招待取消、権限変更、契約変更申請、通知設定変更、CSV出力、CSV取込（初期追加）とする。
- 検索条件は、操作ユーザー、対象種別、対象ID、操作種別、結果、発生日時、IPアドレスを基本とする。
- 保持期間はプラン要件を正本とし、Free 7日、Starter 30日、Business 1年、Enterprise 個別契約とする。期限を超えた操作履歴は操作履歴整理バッチで削除またはアーカイブする。
- 変更前後差分を含む完全な変更履歴は将来拡張とする。

## 8. マイグレーション方針

- DB変更はマイグレーションファイルで管理する。
- 本番適用済みマイグレーションは原則変更せず、新規ファイルで差分適用する。
- 初期データとして、契約プラン、要件定義の7標準ロール、権限マスタ、ロール権限、標準通知設定を投入する。

## 9. バックアップ・リストア方針

| 項目 | 方針 |
|---|---|
| バックアップ頻度 | 日次 |
| 保持期間 | DBバックアップは初期7〜30日を目安。操作履歴はプラン別保持期間（Free 7日、Starter 30日、Business 1年、Enterprise 個別契約）を正本とする |
| リストア確認 | 少なくとも四半期ごとに復元手順を確認し、RTO 4時間以内・RPO 24時間以内を初期目標とする |
| 対象 | DB、CSV履歴ファイル、必要な設定。バックアップは暗号化し、保管先を分離する |

## 10. 後続確認事項

| 項目 | 確認内容 |
|---|---|
| FK適用範囲 | 詳細設計で主要関連へ適用し、論理削除との相性を見て実装時に最終確認する |
| 操作履歴 | 初期必須としてaudit_logへ保存する。変更差分を含む完全な変更履歴は将来拡張として扱う |
| データ保持期間 | 通知ログ・CSV履歴は運用設計で決定する。操作履歴はプラン要件を正本とし、Free 7日、Starter 30日、Business 1年、Enterprise 個別契約で保持する |

## 付録A. Issue対応追補: DB設計方針

### A.1 CIDR範囲重複

同一テナント内のIPサブネットは、完全一致だけでなく範囲重複も禁止する。DBの単純UNIQUEだけでは表現しづらいため、Service/ValidationでCIDR範囲を数値化して既存有効サブネットとの重なりを検証する。必要に応じて `ip_version`, `range_start`, `range_end` 相当の検索補助列を検討する。

### A.2 監査カラム

`created_by` / `updated_by` のNOT NULL方針を維持する。ユーザー操作でない処理は、システムユーザーIDを設定する。履歴系で操作者が意味を持たない場合も、作成処理主体としてシステムユーザーIDを設定する。

### A.3 ID採番

主キー `bigint` はMariaDB `AUTO_INCREMENT`、JPA `GenerationType.IDENTITY` を基本とする。マスタ初期データで固定IDを使う場合は採番衝突を避ける範囲を予約する。

### A.4 タイムゾーン

初期リリースのDB・アプリ基準タイムゾーンは `Asia/Tokyo` とする。DBセッションタイムゾーン、アプリケーション設定、バッチ実行日の算出基準を同一に保つ。テナント別タイムゾーンは将来拡張とする。

### A.5 照合順序・文字列検索

MariaDBの文字コードは `utf8mb4` を基本とし、照合順序は日本語・英数字の大文字小文字を区別しない検索に適したものを採用する。大小文字差は区別しない。全半角・かな差異の同一視が必要な検索は、アプリ側の正規化列または検索用キーワード生成で補う。LIKE検索が多い項目は、前方一致・完全一致用インデックスと部分一致検索の性能要件を分けて設計する。

## 付録B. Issue対応追補: 主なテーブル領域の補完

主なテーブル領域はER図・詳細設計の初期対象と整合させる。

| 領域 | 追加・補完対象 |
|---|---|
| テナント・契約 | `contract_change_request` |
| ユーザー・権限 | `password_reset_token`, `user_invitation_token`, `permission`, `role_permission` |
| ラックテンプレート | `rack_template`, `rack_template_item` |
| 連絡先・タグ・別名 | `resource_alias` |
| 保守契約 | `maintenance_contract_contact` |

以後、ER図の主要テーブル一覧に初期対象として追加したテーブルは、本方針の領域表にも反映する。
