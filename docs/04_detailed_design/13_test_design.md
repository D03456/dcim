# 4. 詳細設計 - テスト設計

## 1. 目的

本書は、本システムの実装時に必要なテスト分類、重点観点、完了基準を定義する。

## 2. テスト分類

| 分類 | 対象 | 主な観点 |
|---|---|---|
| Unit Test | Value Object、Domain Service | 入力制約、状態遷移、境界値 |
| Application Service Test | ユースケース | 権限、テナント分離、上限、トランザクション |
| Repository Test | JPA Repository | tenant_id条件、deleted=false、一意制約 |
| Integration Test | DB、メール、CSV | 実DB接続、通知ログ、CSV履歴 |
| Vaadin UI Test | 画面 | 画面遷移、ボタン制御、エラー表示 |
| Batch Test | Scheduler処理 | 期限通知、Free期限超過、失敗継続 |

## 3. 重点テスト観点

## 3.1 テナント分離

- 他テナントのデータを参照できないこと。
- DTOで他テナントIDを指定しても無視または拒否されること。
- Repository検索に `tenant_id` と `deleted=false` が含まれること。

## 3.2 権限

- 閲覧者は登録・更新・削除できないこと。
- 契約管理者は契約関連のみ操作できること。
- 7ロール（システム管理者、テナント管理者、契約管理者、運用管理者、編集者、閲覧者、監査担当者）の権限マトリクスが要件・基本設計と一致すること。
- テナント管理者のみユーザー招待・権限変更ができること。
- 運用管理者/編集者/閲覧者/監査担当者/契約管理者の操作可否が画面・Service層で一致すること。
- 初期テナント管理者の通常ユーザー削除・無効化が拒否されること。
- テナント解約フローでは初期テナント管理者が利用停止扱いになること。

## 3.3 Freeトライアル期限超過

- `TRIAL_EXPIRED` でもログイン・参照・CSVエクスポートできること。
- 登録・更新・削除・CSVインポート・ユーザー招待が拒否されること。
- 有料プラン変更は可能であること。
- 更新不可時に適切な日本語メッセージが表示されること。

## 3.4 プラン上限

- DC、ラック、機器、管理対象IP、タグ、ユーザーの上限を超える登録が拒否されること。
- IP上限追加、機器追加のオプションが上限に反映されること。
- 論理削除済みデータはカウント対象外であること。

## 3.5 IP管理

- CIDR重複が拒否されること。
- 個別IPが所属サブネット範囲内であること。
- 使用中IPの二重割当ができないこと。

## 3.6 ラック配置

- U位置の範囲外指定が拒否されること。
- 同一ラック内でU位置が重複しないこと。
- ラック高さ変更時に既存機器を下回る値が拒否されること。
- フロア図が行・列のグリッドで表示され、ラック列・ラック位置を確認できること。
- ラック図がU単位の縦グリッドで表示され、搭載機器・空きU・重複不可状態を確認できること。

## 3.7 通知

- 保守期限60日前、30日前、当日、期限切れ通知が対象になること。
- メール通知と画面内通知がチャネル単位で作成されること。
- 画面内通知の未読・既読がユーザー単位で管理されること。
- Free期限3日前・期限日通知が対象になること。
- 保守期限通知の対象がテナント管理者、運用管理者、編集者、保守契約連絡先であり、DC連絡先・機器担当者が初期対象外であること。
- プラン上限通知がテナント管理者・契約管理者に届き、管理対象IP数で80%警告・100%到達を判定すること。
- ユーザー招待通知、パスワード再設定通知、操作エラー通知が通知ログに残ること。
- 同一対象・同一チャネル・同一宛先への重複通知が抑止されること。
- メール送信失敗時にFAILEDとして記録されること。

## 3.8 リージョン・ユーザー・呼称名

- リージョン名の同一テナント内重複が拒否されること。
- DCで利用中のリージョン削除が拒否またはINACTIVE化されること。
- ユーザー招待時にメール重複とユーザー数上限が検証されること。
- パスワード平文がDB・ログ・通知に残らないこと。
- パスワード再設定依頼でメール存在有無を推測できないこと。
- 有効期限切れ・使用済み再設定トークンが拒否されること。
- 管理者がユーザー詳細から再設定メールを再送できること。
- ResourceAliasの同一対象内重複が拒否され、検索対象になること。
- 機器別名を追加・削除でき、機器一覧/横断検索で検索対象になること。
- 機器タグを付与・解除でき、タグ重複付与が拒否されること。
- ラックテンプレートを登録・複製し、テンプレートからラックを作成できること。
- ラックテンプレート明細のU範囲外・重複が拒否されること。

## 3.9 CSV

- CSVエクスポートが権限・検索条件・テナント分離を反映すること。
- CSVインポートでヘッダ不正、必須欠落、形式不正、参照なし、上限超過が検出されること。
- 行単位エラーが `csv_import_error` に保存されること。

## 3.10 画面詳細設計追跡

- SCR-001〜SCR-041について、画面項目、ボタン活性、エラー表示、権限別表示制御の詳細化Issueが未完了のまま実装着手されないこと。
- 認証、通知、操作履歴、テナント管理、CSV、プラン上限の主要画面は受入テストで画面状態を確認すること。

## 4. テストデータ方針

- 複数テナントを用意し、テナント分離を検証する。
- Free / Starter / Business / Enterprise の各プランを用意する。
- 期限前、期限日、期限超過のFreeテナントを用意する。
- 権限別ユーザーを用意する。
- ラックU重複、CIDR重複、保守期限などの境界データを用意する。

## 5. 完了基準

- 主要Application Serviceの正常系・異常系がテストされていること。
- 権限、テナント分離、Free期限超過制御のテストがあること。
- Repositoryのtenant_id / deleted条件が検証されていること。
- バッチ、通知、CSV、リージョン、ユーザー、呼称名・別名の主要ケースが検証されていること。
- `git diff --check`、ビルド、テストが成功していること。


## 3.11 例外・ログ・通知境界テスト

- 認可拒否、他テナントアクセス疑い、SystemException発生時に内部詳細が画面表示されず、WARN/ERRORログと `request_id` が残ること。
- 監査ログ記録失敗時に業務処理をロールバックするか、運用アラートを出すかの方針どおりに動作すること。
- 保守期限通知の60日前/30日前/当日/期限切れが別々に重複抑止され、いずれかの送信済みが他タイミングを抑止しないこと。
- 通知設定OFF、メールのみ、画面内のみ、FAILED後再送、外部連絡先メール未設定時のSKIPPEDが期待どおり記録されること。
- OPERATION_ERRORが同一発生元・対象・当日内で集約され、`occurrence_count` と `retry_required` が更新されること。

## 付録A. Issue対応追補: 監査ログイベント別テスト

| イベント | テスト観点 |
|---|---|
| ログイン成功/失敗 | 操作者、結果、IPアドレス、ユーザー推測につながる情報の非表示 |
| CRUD操作 | 対象種別、対象ID、操作種別、成功/失敗、テナントID |
| ユーザー招待/再招待/取消 | トークン値を保存しないこと、対象ユーザー、操作者 |
| 権限変更 | 変更前後ロール、操作者、対象ユーザー |
| CSVエクスポート | 出力対象、件数、マスキング、権限、request_id |
| プラン/オプション変更申請 | 申請者、対象プラン/オプション、結果 |
| 通知設定変更 | 変更対象、変更前後、操作者 |
| システム管理者のテナント操作 | 対象テナント、操作種別、結果、テナントスコープ例外 |

各イベントで、検索画面に表示できる項目とマスキング対象も確認する。

## 付録B. Issue対応追補: 通知・認可・秘匿テスト

### B.1 プラン上限通知

WARNING / REACHED / EXCEEDED / RECOVERED の各レベルについて、発火条件、再通知抑止、改善時の抑止解除をテストする。

### B.2 TRIAL_EXPIREDとPermission

TRIAL_EXPIRED状態でも通常Permissionが必要であることを確認する。例: CSV権限がない契約管理者はCSVエクスポート不可、VIEW権限がない画面は参照不可、更新系はPermissionがあっても拒否。

### B.3 パスワード再設定/招待通知ログ秘匿

`PASSWORD_RESET` / `USER_INVITATION` の通知ログについて以下を確認する。

- `action_url` にトークン付きURLが保存されないこと
- `body` に本文全文・トークン値・秘密情報が保存されないこと
- `recipient` や `error_message` がマスキング/ハッシュ化方針どおりであること
- FAILED時も外部送信エラー詳細に秘密情報が含まれないこと
