# 4. 詳細設計 - レビュー確認事項一覧

## 1. 目的

本書は、実装着手前およびPRレビュー時に確認すべき詳細設計観点を整理する。

## 2. 優先度A：実装前に確認必須

| 観点 | 確認内容 |
|---|---|
| 要件整合 | 要件定義・基本設計と矛盾していないか |
| 初期/将来分離 | クラウド連携、監査ログなど将来拡張が初期必須に混入していないか |
| テナント分離 | すべての業務検索でtenant_idを条件に含める設計か |
| 権限 | 画面だけでなくService層で認可する設計か |
| Free期限超過 | TRIAL_EXPIRED時の許可/禁止操作が一貫しているか |
| プラン上限 | DC、ラック、機器、IPサブネット、管理対象IP、タグ、ユーザーの上限が統一されているか |
| IP管理 | IPサブネット数上限と管理対象IP数上限が別々に定義されているか |
| ラック上限 | ラック列ではなくラック数が上限対象になっているか |
| 監査情報 | created_by/created_at/updated_by/updated_at が主要データにあるか |
| Value Object | 初期必須Value Object（CIDR、IP、ラックU範囲、通知日数、メール、日付期間）が導入または実装計画に含まれているか |

## 3. 優先度B：実装中に確認

| 観点 | 確認内容 |
|---|---|
| パッケージ構成 | PresentationからRepositoryを直接呼ばないか |
| DTO境界 | Entityを画面へ直接返していないか |
| 排他制御 | ラックU配置、IP割当、CSVインポート同時実行の競合対策があるか |
| トランザクション | Application Serviceに境界があるか |
| 例外 | 内部エラーを画面に出さないか |
| ログ | 秘密情報・個人情報をログ出力していないか |
| 通知 | 通知ログ、重複抑止、失敗時FAILEDが設計されているか |
| CSV | 履歴・行単位エラー・権限制御があるか |
| バッチ | テナント単位で失敗分離できるか |

## 4. 優先度C：リリース前に確認

| 観点 | 確認内容 |
|---|---|
| バックアップ | DBバックアップ・復元手順が確認されているか |
| 監視 | アプリ死活、DB容量、バッチ失敗、メール失敗を検知できるか |
| ログ保持 | アプリログ、通知ログ、CSV履歴の保持期間が決まっているか |
| SMTP | 本番SMTPサービスと送信元ドメインが決まっているか |
| CSV文字コード | Excel利用を考慮した文字コード方針が決まっているか |
| 画面モック | 後工程で画面詳細・モックと設計が一致しているか |

## 5. PRレビュー時の判定

| 判定 | 内容 |
|---|---|
| Approve | 要件・設計・テスト観点を満たす |
| Comment | 軽微な表現、補足、後続Issueでよい |
| Request changes | テナント分離、権限、データ整合性、セキュリティに問題がある |

## 6. レビューコメント方針

- 指摘はファイル名、該当箇所、理由、修正案をセットにする。
- 確認が必要なものは無理に修正せず、Issue化する。
- 画面モックに依存する内容は後工程Issueとして分離する。
