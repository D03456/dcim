# 4. 詳細設計 - トランザクション設計

## 1. 目的

本書は、本システムのトランザクション境界、ロールバック方針、排他制御、外部連携との整合性方針を定義する。

## 2. 基本方針

- トランザクション境界はApplication Service層に置く。
- 参照系は `readOnly=true` を基本とする。
- 更新系は1ユースケースを1トランザクションの基本単位とする。
- メール送信やファイル出力などの外部I/OはDB更新と分離する。

## 3. 処理別トランザクション

| 処理 | 方針 |
|---|---|
| 登録・更新・削除 | `REQUIRED` |
| 一覧・詳細参照 | `readOnly=true` |
| CSVエクスポート | 検索はreadOnly、履歴保存は別トランザクション |
| CSVインポート | ファイル単位または行単位。初期は行単位エラー管理を優先 |
| 通知ログ作成 | 送信前にPENDINGで保存 |
| メール送信結果更新 | 送信後にSENT/FAILEDを別更新 |
| バッチ | テナント単位または対象単位で分割 |

## 4. ロールバック方針

| ケース | 方針 |
|---|---|
| 入力チェックエラー | DB更新前に終了 |
| 業務例外 | トランザクションをロールバック |
| 一意制約違反 | ロールバックし、業務エラーへ変換 |
| メール送信失敗 | 業務データはロールバックせず、通知ログをFAILEDに更新 |
| CSV行エラー | 対象行のみ失敗扱い。可能な範囲で他行継続 |
| バッチ一部失敗 | 対象テナントまたは対象レコードのみ失敗扱い |

## 5. 排他制御

| 対象 | 方針 |
|---|---|
| 機器登録 | 正式名称・ホスト名・シリアル番号の重複はDB制約またはServiceで防止 |
| ラックU配置 | 同一ラック内U範囲をServiceで検証し、保存直前に対象ラックの機器配置を再検索して重複確認する。競合時は業務例外で中断する |
| IP割当 | 割当前に対象IPを再取得し、`UNUSED` または `RESERVED` の場合のみ更新する。競合時は業務例外で中断する |
| プラン上限 | 登録直前に現在数を再確認する |
| CSVインポート | 同一テナント・同一target_typeの同時取込を禁止する。処理中履歴が存在する場合は新規取込を拒否する |

## 6. 外部連携との整合性

- メール送信はDBトランザクション内で直接完結させない。
- 通知ログをPENDINGで作成し、送信結果を別途更新する。
- CSVエクスポート履歴はファイル生成成功後に記録するか、開始・完了ステータスを持つ。
- 将来のクラウドAPI連携は、同期結果の履歴と失敗再実行を前提に設計する。

## 7. Freeトライアル期限処理

- 期限確認バッチはテナント単位で処理する。
- `trial_end_date < 現在日付` のFreeテナントを `TRIAL_EXPIRED` に更新する。
- すでに有料プランへ変更済みのテナントは対象外とする。
- 期限超過通知と状態更新は、失敗時の再実行を考慮して冪等にする。

## 8. 実装注意

- `@Transactional` はApplication Serviceのpublicメソッドに付与する。
- 同一クラス内の自己呼び出しによるトランザクション未適用に注意する。
- 長時間処理は1トランザクションにしない。
- 例外を握りつぶして正常終了扱いにしない。


## 9. 排他制御の実装方針

| 対象 | 初期実装方針 |
|---|---|
| ラックU配置 | 保存直前に同一ラック内の既存機器配置を再検索し、U範囲重複がないことを確認する。重複があれば `DuplicateResourceException` または業務例外で中断する |
| IP割当 | 対象IPを更新直前に再取得し、割当可能状態であることを確認する。すでに `IN_USE` の場合は中断する |
| プラン上限 | 登録直前に現在件数を再取得し、上限到達済みの場合は中断する |
| CSVインポート | `csv_import_history` に同一テナント・同一target_typeの処理中レコードがある場合は新規取込を拒否する |

将来、複数台構成や高頻度更新が必要になった場合は、楽観ロック用のversionカラムまたはDBロックの導入を再検討する。
