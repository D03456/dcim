# 4. 詳細設計 - ログ設計

## 1. 目的

本書は、本システムのアプリケーションログ、業務イベントログ、通知ログ、CSV履歴、初期必須の操作履歴に関する方針を定義する。

## 2. ログ分類

| 分類 | 内容 | 初期対象 |
|---|---|:---:|
| アプリケーションログ | 起動、エラー、処理状況 | ○ |
| アクセスログ | HTTPアクセス、ステータス | ○ |
| 業務イベントログ | 重要な業務処理の開始・完了 | △ |
| 通知ログ | メール通知の送信結果 | ○ |
| CSV履歴 | CSV出力・取込履歴 | ○ |
| 監査ログ | ログイン成功/失敗、CRUD、招待、権限変更、CSV出力、契約変更、プラン変更申請の証跡 | ○ |

## 3. ログレベル

| レベル | 用途 |
|---|---|
| ERROR | 処理継続不能、外部連携失敗、DB障害 |
| WARN | 業務上の異常、再試行可能な失敗、権限拒否 |
| INFO | 起動停止、バッチ開始終了、重要業務イベント |
| DEBUG | 開発・調査用。原則本番では抑制 |

## 4. 出力項目

| 項目 | 内容 |
|---|---|
| timestamp | 発生日時 |
| level | ログレベル |
| tenant_id | 分かる場合のみ出力 |
| user_id | 分かる場合のみ出力 |
| request_id | リクエスト相関ID |
| operation | 処理名 |
| result | 成功・失敗 |
| error_code | 業務エラーコード |

## 5. 出力禁止・マスキング

以下はログに出力しない。

- パスワード
- APIキー、SMTPパスワード、クラウド認証情報
- セッションID、認証トークン
- CSVファイルの全内容
- 必要以上の個人情報
- SQL全文やスタックトレースの画面表示

## 6. 重要イベントログ

| イベント | 方針 |
|---|---|
| ログイン成功/失敗 | 初期必須として監査ログへ保存 |
| テナント作成・状態変更 | INFO |
| プラン変更 | INFOに加え、初期必須として監査ログへ保存 |
| Free期限超過状態への変更 | INFO |
| 主要データ登録・更新・削除 | 初期必須として監査ログへ保存。created_by/updated_byも併用 |
| CSVエクスポート | CSV履歴と監査ログへ保存 |
| CSVインポート | 取込履歴・行エラーへ保存 |
| メール送信 | 通知ログへ保存 |

## 7. 保持期間

| ログ | 初期方針 |
|---|---|
| アプリケーションログ | 7〜30日を目安 |
| アクセスログ | 7〜30日を目安 |
| 通知ログ | 業務確認用にDB保持。期間は運用設計で確定 |
| CSV履歴 | 問い合わせ対応に必要な期間保持 |
| 監査ログ | 初期必須としてDB保持する。保持期間はプラン要件・運用設計に従い、少なくともSCR-032で検索可能にする |

## 8. 実装注意

- 例外発生時も利用者向けメッセージと内部ログを分離する。
- 権限拒否や他テナントアクセス疑いはWARNで記録する。
- バッチは開始、終了、対象件数、失敗件数を記録する。
- 通知・CSV・操作履歴は専用テーブルに履歴を残し、アプリログだけに依存しない。


## 9. request_id / correlation_id（基本方針）

画面操作・Service処理・通知・バッチには `request_id` を採番し、MDCへ設定してアプリケーションログと業務ログに出力する。バッチや通知の子処理では親の `correlation_id` を引き継ぎ、利用者向けエラー画面には内部詳細ではなく問い合わせIDとして `request_id` を表示する。

`audit_log` には操作画面で検索・表示できる粒度として `actor_user_id`、`occurred_at`、`summary`、`target_name`、必要に応じてマスキング済み `detail_json` を保持する。秘密情報、パスワード、トークン、メール本文中の機微情報は保存しない。

## 10. request_id / correlation_id（DB履歴連携）

アプリログの `request_id` は、監査ログ・通知ログ・CSV履歴などDB履歴にも可能な限り保存する。バッチや非同期処理では `correlation_id` を処理全体の追跡キーとして保存する。

| 履歴 | 追跡キー |
|---|---|
| `audit_log` | `request_id` |
| `notification_log` | `request_id`, `correlation_id` |
| `csv_export_history` | `request_id` |
| `csv_import_history` | `request_id`, `correlation_id` |
| `batch_execution_log` | `correlation_id` |

## 11. 履歴保持期間の暫定方針

| 対象 | 暫定保持期間 | 備考 |
|---|---:|---|
| アプリログ | 90日 | 個人情報・秘密情報は出力禁止 |
| 監査ログ | 1年 | プラン要件で延長する可能性あり |
| 通知ログ | 180日〜365日 | 失敗ログは長めに保持 |
| CSV履歴 | 90日〜180日 | 一時ファイルはより短く保持 |

正式な保持期間は運用設計で確定するが、初期リリース時点では上記を実装の暫定値とする。

## 付録B. Issue対応追補: 監査ログ保持期間・保存失敗方針

### B.1 操作履歴/監査ログ保持期間

操作履歴/監査ログの保持期間は料金プラン要件を正本とする。

| プラン | 操作履歴/監査ログ保持期間 |
|---|---:|
| Free | 7日 |
| Starter | 30日 |
| Business | 1年 |
| Enterprise | 個別契約 |

アプリケーションログの暫定保持期間は30日とする。障害調査で長期保持が必要な情報は、監査ログ・通知ログ・CSV履歴などDB履歴側へ必要最小限で保存する。

### B.2 監査ログ保存失敗時のログ方針

監査ログ保存失敗時は `ERROR` で `request_id`, `eventType`, `targetType`, `targetId`, `actorUserId` を出力し、秘密情報は出さない。統制上必須の操作は業務処理をロールバックし、継続許容操作ではOPERATION_ERROR通知を作成する。
