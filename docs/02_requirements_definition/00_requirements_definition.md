# 要件定義案

## 1. 目的

本書は、Data Center Asset & Infrastructure Manager の初期開発に向けた要件定義案を整理するものである。

本システムは、データセンター、ラック、機器、IPサブネット、保守契約、ユーザー、プラン情報を一元管理し、インフラ資産管理業務の効率化を目的とする。

## 2. 前提条件

| 項目 | 内容 |
|---|---|
| 開発手法 | ウォーターフォール |
| 設計方針 | DDDを意識した設計 |
| アプリ形態 | Webアプリケーション / SaaS |
| バックエンド | Java / Spring Boot |
| 認証・認可 | Spring Security |
| UI | Vaadin |
| DB | MariaDB |
| ビルド | Maven |
| 補助ライブラリ | Lombok |
| 開発支援 | OpenClaw |

## 3. システム利用者

| 利用者 | 説明 |
|---|---|
| システム管理者 | 全体設定、プラン、テナント管理を行う |
| テナント管理者 | 自社テナント内のユーザー、DC、機器などを管理する |
| 一般ユーザー | 登録済み情報の閲覧、更新を行う |
| 閲覧ユーザー | 登録済み情報の参照のみ行う |

## 5. プラン要件

### 5.1 プラン一覧

| プラン | 利用形態 | DC上限 | ラック上限 | 機器上限 | サブネット上限 | ユーザー上限 |
|---|---|---:|---:|---:|---:|---:|
| Free | 14日間トライアル | 1 | 3 | 20 | 3 | 1 |
| Starter | 月額 / 年額 | 2 | 5 | 50 | 10 | 3 |
| Business | 月額 / 年額 | 5 | 50 | 100 | 50 | 10 |
| Enterprise | 個別契約 | 10 | 100 | 1000 | 200 | 30 |

### 5.2 Freeプラン方針

- Freeプランは14日間のトライアル利用を目的とする。
- 小規模ながら現実的な評価ができるよう、DC 1件、ラック3本、機器20台、サブネット3件、ユーザー1名まで登録可能とする。
- トライアル終了後も継続利用する場合は、有料プランへの移行を促す。

### 5.3 オプション要件

| オプション | 単位 | 内容 |
|---|---:|---|
| サブネット追加 | 10サブネット単位 | プラン上限に加算する |
| 機器追加 | 100台単位 | プラン上限に加算する |

### 5.4 上限制御

- 各テナントは契約プランに応じた上限を持つ。
- 上限を超えるデータ登録は不可とする。
- オプション契約がある場合は、基本上限にオプション分を加算する。
- 上限到達時は、登録画面で理由を表示する。

## 6. 機能要件

## F-001 認証機能

### 概要

ユーザーがメールアドレスとパスワードでログインできる。

### 要件

- ログインできること。
- ログアウトできること。
- 未ログインユーザーは管理画面にアクセスできないこと。
- パスワードはハッシュ化して保存すること。

## F-002 テナント管理機能

### 概要

SaaS利用単位としてテナントを管理する。

### 要件

- テナントを登録、編集、削除できること。
- テナントごとに契約プランを設定できること。
- テナントごとにデータを分離すること。
- 他テナントのデータは閲覧・更新できないこと。

## F-003 ユーザー管理機能

### 概要

テナント内の利用者を管理する。

### 要件

- ユーザーを登録、編集、無効化できること。
- ユーザーにロールを設定できること。
- プラン上限を超えるユーザー登録はできないこと。

## F-004 データセンター管理機能

### 概要

データセンターの基本情報を管理する。

### 管理項目

- データセンター名
- 正式名称
- 呼称名・別名
- 地域
- 都道府県
- 住所
- 備考
- タグ

### 要件

- データセンターを登録、編集、削除できること。
- 連絡先を紐づけられること。
- プラン上限を超える登録はできないこと。

## F-005 連絡先管理機能

### 概要

データセンターや保守契約に関連する連絡先を管理する。

### 管理項目

- 連絡先名
- 会社名
- 部署名
- 担当者名
- メールアドレス
- 電話番号
- 備考

### 要件

- 連絡先を別エンティティとして管理すること。
- データセンター、保守契約などに紐づけられること。

## F-006 ロケーション階層管理機能

### 概要

データセンター内の物理的な配置階層を管理する。棟、フロア、エリア、ラック列は初期リリースから必須の階層として扱う。

### 対象

- 棟
- フロア
- エリア
- ラック列
- ラック

### 要件

- データセンター配下に棟を登録できること。
- 棟配下にフロアを登録できること。
- フロア配下にエリアを登録できること。
- エリア配下にラック列を登録できること。
- ラック列配下にラックを登録できること。
- エリアには東・西・南・北などの区分を設定できること。

## F-007 ラック管理機能

### 概要

ラックの基本情報、搭載可能U数、設置場所を管理する。

### 管理項目

- ラック名
- 正式名称
- 呼称名・別名
- ラック列
- 高さ
- 備考
- タグ

### 要件

- ラックを登録、編集、削除できること。
- ラック高さを管理できること。
- プラン上限を超えるラック登録はできないこと。
- 将来的にラックテンプレートに対応できる構造とすること。

## F-008 機器管理機能

### 概要

サーバー、ネットワーク機器などを管理する。

### 対象機器

- サーバー
- スイッチ
- ルーター
- ファイアウォール
- ロードバランサー
- その他機器

### 管理項目

- 機器名
- 正式名称
- 呼称名・別名
- 機器種別
- メーカー
- 型番
- シリアル番号
- 設置ラック
- 搭載開始U
- 搭載U数
- ステータス
- 備考
- タグ

### 要件

- 機器を登録、編集、削除できること。
- ラックに紐づけられること。
- IPアドレスを紐づけられること。
- 保守契約を紐づけられること。
- プラン上限を超える機器登録はできないこと。
- 保守契約が未紐づけの機器を検索できること。

## F-009 IPサブネット管理機能

### 概要

IPサブネットと配下のIP利用状況を管理する。

### 管理項目

- IPサブネット
- CIDR
- ネットワーク区分
- 利用状態
- 紐づけ機器
- 用途
- 備考
- タグ

### 要件

- IPサブネットを登録、編集、削除できること。
- サブネット配下の個別IP利用状況を機器に紐づけられること。
- 未使用IPを検索できること。
- プラン上限を超えるサブネット登録はできないこと。
- オプション契約によりサブネット上限を追加できること。

## F-010 保守契約管理機能

### 概要

機器に紐づく保守契約を管理する。

### 管理項目

- 契約名
- 契約会社
- 連絡先
- 契約開始日
- 契約終了日
- 対象機器
- 契約内容
- 備考

### 要件

- 保守契約を登録、編集、削除できること。
- 複数機器を保守契約に紐づけられること。
- 機器側から保守契約を確認できること。
- 保守契約側から対象機器を確認できること。
- 保守契約がない機器を検索できること。
- 保守終了2か月前に通知対象として抽出できること。

## F-011 タグ管理機能

### 概要

検索性向上のため、各管理対象にタグを付与する。

### 対象

- データセンター
- ラック
- 機器
- IPアドレス
- 保守契約
- クラウドリソース

### 要件

- タグを登録、編集、削除できること。
- 対象データに複数タグを付与できること。
- タグで検索できること。

## F-012 呼称名・別名管理機能

### 概要

正式名称以外の名称で検索できるようにする。

### 要件

- データセンター、ラック、機器、ネットワーク機器に呼称名・別名を登録できること。
- 1つの対象に複数の別名を登録できること。
- 正式名称、呼称名、別名で検索できること。

## F-013 通知機能

### 概要

保守契約の期限切れ予定を通知する。

### 要件

- 保守終了日の2か月前に通知対象とすること。
- 通知対象一覧を表示できること。
- 将来的にメール通知に拡張できる構造とすること。

## F-014 検索機能

### 概要

登録済み情報を横断検索する。

### 要件

- 名称、正式名称、呼称名、別名で検索できること。
- タグで検索できること。
- 機器種別で検索できること。
- 保守契約有無で検索できること。
- 保守期限で検索できること。
- 未使用IPで検索できること。

## F-015 クラウドリソース管理機能

### 概要

将来拡張としてクラウドリソースを管理する。

### 対象

- AWSアカウント
- AWSリージョン
- EC2
- コンテナ
- EKS Pod

### 要件

- 初期開発では詳細実装を必須としない。
- ドメイン設計上、将来追加しやすい構造とすること。

## 7. 非機能要件

## NF-001 セキュリティ

- テナント間のデータ分離を行うこと。
- パスワードは平文保存しないこと。
- 認証済みユーザーのみ管理画面へアクセスできること。
- ロールに応じて操作権限を制御できること。

## NF-002 性能

- 一覧画面は通常利用時に実用的な速度で表示できること。
- 検索条件に応じたDBインデックスを設計すること。
- 将来的なデータ増加を考慮すること。

## NF-003 可用性

- 単一障害点を最小化できる構成を検討すること。
- 初期開発では小規模SaaSとして運用可能な構成を優先すること。

## NF-004 保守性

- DDDを意識し、ドメインごとに責務を分離すること。
- Java / Spring Boot / Vaadin の標準的な構成を採用すること。
- OpenClawでレビューしやすいよう、命名規則と設計ルールを統一すること。

## NF-005 拡張性

- クラウドリソース管理を後から追加できること。
- プランやオプションを追加しやすい構造にすること。
- 外部API連携を将来的に追加できること。

## NF-006 監査性

- 初期開発では必須ではないが、将来的に操作ログを記録できる構造を検討すること。

## 11. 業務ルール案

| ルールID | 内容 |
|---|---|
| BR-001 | テナントごとにデータを分離する |
| BR-002 | プラン上限を超える登録は不可 |
| BR-003 | サブネット追加オプションは10サブネット単位 |
| BR-004 | 機器追加オプションは100台単位 |
| BR-005 | Freeプランは14日間トライアルとし、DC 1件、ラック3本、機器20台、サブネット3件、ユーザー1名まで |
| BR-006 | 保守契約終了日の2か月前から通知対象 |
| BR-007 | 機器は0個以上のIPアドレスを紐づけ可能 |
| BR-008 | 保守契約は複数機器を対象にできる |
| BR-009 | 正式名称以外に複数の呼称名・別名を持てる |
| BR-010 | 各管理対象に複数タグを付与できる |

## 12. 優先度

| 優先度 | 内容 |
|---|---|
| Must | 認証、テナント、ユーザー、DC、ラック、機器、IP、保守契約、プラン上限制御 |
| Should | タグ、呼称名・別名、未保守機器検索、保守期限通知 |
| Could | CSVインポート/エクスポート、ラックテンプレート、簡易ダッシュボード |
| Won't | AWS自動連携、高度ラック図、外部API、SSO |
